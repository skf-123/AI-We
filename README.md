## 两个入口：贴代码 / 整个项目

产品有**两个并列的入口**，不是替代关系：

| 入口 | 输入 | 状态 |
|---|---|---|
| **贴代码** | 一段代码 | ✅ 已实现（线上可用） |
| **整个项目** | 一个文件夹；zip 在后续里程碑 | 🟡 第一里程碑已实现并走查；zip 未做 |

网站首页先讲产品能帮什么，再让人选入口：贴代码在 `/code`，整个项目在 `/project`。

**为什么第二个才是产品真正的形态**：真实的学习场景里，人手上往往不是"一段代码"，而是**一整个项目**。
贴代码是入口的妥协版 —— 它要求用户**自己先挑出**"哪一段值得看"。

**项目入口第一里程碑已完成**（文件夹拖入）：

- **两步走**：先出一张**项目地图**（目录里每个文件夹是干什么的），**再逐文件解析**
- 目录树分三档：**用户自己写的代码读内容**；配置文件默认只作上下文（可切换成仍需解释）；
  依赖 / 编译产物 / 二进制 / 锁文件**只登记位置与跳过原因**
- 文件级只出**四段文字**；项目级另外只出**一张图** —— 讲清"文件与文件之间的流程"
- 多文件**并发解析**，一个文件一路流式请求 —— 这也是**必须上 HTTP/2** 的原因：
  HTTP/1.1 同源只有 6 条连接，本地实测并发 40 比并发 5 **慢 6 倍**
- 全部文件解析完后，由用户点「生成项目总览 + 项目图」，不做自动汇总

## 系统架构

### 一次请求的完整链路

```
浏览器（app/pages/code.vue）
   │  POST /api/analyze  { code }
   ▼
Nuxt 服务端（server/api/analyze.post.ts）
   │
   ├─ ① 校验请求 ────────────── Zod 校验 code 长度 1~20000 字
   │
   ├─ ② 知识库检索 ────────────► server/rag/
   │      · 判断代码语言（未收录的语言如 C++ 直接跳过检索）
   │      · 把代码变成向量（调智谱 embedding-3）
   │      · 在内存里逐条算余弦相似度，取分数 ≥0.38 的前 4 条
   │
   ├─ ③ 组装提示词 ──────────── server/utils/prompt.ts
   │      · 系统提示词（四段输出的格式规范）
   │      · ＋ 参考资料使用规则（**只在检索到资料时才追加**）
   │      · ＋ 用户代码 ＋ 检索到的参考资料
   │
   ├─ ④ 调大模型 ────────────── DeepSeek，stream: true
   │
   ├─ ⑤ 流转发 ──────────────── 把上游 SSE 拆成纯文本流 → 浏览器（打字机效果）
   │
   └─ ⑥ 引用来源 ────────────── 放进响应头 X-Rag-Sources → 浏览器（引用卡片）
```

### 核心设计

系统由下面十一部分组成。每一部分都是为解决一个具体问题而设计的。

| # | 模块 | 在哪 | 它解决什么问题 |
|---|---|---|---|
| 1 | **提示词** —— 五段输出规范、详略控制、诚实性要求、安全提示规则 | `server/utils/prompt.ts` | 把"用户不知道该怎么问"翻译成"必须自动输出什么、讲到多细" |
| 2 | **知识库语料** —— 58 条技术资料，逐条整理，每条带官方出处 | `server/rag/corpus.json` | 让"技术溯源"有据可查，而不是凭模型的记忆 |
| 3 | **检索机制** —— 语言过滤 + 向量检索 + 阈值实测校准 | `server/rag/retrieve.ts` | 从语料里找出"这段代码用到的那几条" |
| 4 | **数据契约** —— 知识框架图的 JSON 结构（代码 / 技术 / 概念三类节点） | `prompt.ts` + `GraphView.vue` | 让"画一张图"变成渲染一份结构化数据 |
| 5 | **引用机制** —— 服务端生成编号 → 响应头传递 → 前端卡片 | `analyze.post.ts` + `SourceList.vue` | 让每一条引用都能点开、对应到具体资料 |
| 6 | **流式实现** —— SSE 拆解、逐字转发 | `server/api/analyze.post.ts` | 打字机效果，不用等全部生成完才看到内容 |
| 7 | **前端界面** —— 布局、流式渲染、知识框架图、引用卡片、浅色主题 | `app/` | 把上面这些能力变成能用的产品 |
| 8 | **降级体系** —— 检索不到 / 服务不可用 / 遇到未收录的语言 | 散在各处 | 任何一环出问题都优雅退回，不报错、不白屏 |
| 9 | **离线工具** —— 向量预计算脚本 + 检索阈值校准探针 | `scripts/` | 让检索质量可以被测量和调优，而不是拍脑袋 |
| 10 | **工程决策与文档** —— 不做独立后端、不装向量数据库、以及 `docs/` 里的说明 | `README.md` + `docs/` | 记录"为什么这么选"，让方案可解释 |
| 11 | **交互层** —— 术语/引用可点、选中正文联动左栏高亮、就地多轮追问 | `app/components/` + `app/utils/` | 把"读完了还有疑问"接住，而不是让用户自己再去搜 |

### 两个关键设计决策

**① 引用来源走 HTTP 响应头，而不是让大模型输出**

检索在流式回答开始**之前**就完成了，所以"检索到哪几条"是服务端**已经确定的事实**。
让大模型再复述一遍只会引入幻觉和截断，而且卡片要等全文流完才出现。

放进响应头（`X-Rag-Sources`）之后：来源 100% 准确，卡片在打字机刚启动时就能显示。

**② 检索前先做语言过滤**

实测发现：**embedding 模型分不开"相关"和"不相关"** —— C++ 代码对 JS 语料也能拿到 0.57 的相似度，
因为向量空间里"这是代码"的权重远大于"这是关于什么的"。

所以检索前先判断代码语言，只在该语言的资料里找；遇到没收录的语言（C++、Go 等）直接跳过检索，
干净地降级为纯模型回答。详见 `server/rag/retrieve.ts` 顶部的注释。

## 交互层（可点、可追问）

主链路负责"把代码讲一遍"，讲完之后的疑问由这一层接住。

**① 术语可点**

「四、技术溯源」里的名词（PEP、ES5、JIT、GIL…）可以点开看解释和官方出处。
词表单独放在 `app/data/glossary.json`，**没有**并进 `server/rag/corpus.json` ——
语料是给向量检索用的，混进去会被当成检索候选、可能挤掉本该命中的段落，
而且改它必须重跑 `rag:build` 重新校准阈值。词表只给前端用，不参与检索。
（术语在**正文的每一段**都可点 —— 判断标准只有一条：这个词收进了词表。
收进来就意味着"它值得单独解释"，那它在哪一段出现都值得解释。
所以可不可点由词表决定，不由它在第几段决定。第五段的图 JSON 不是正文，不参与。）

出处的取法：**以各语言的官方文档为主**（MDN、Python 文档术语表、ECMA-262、框架文档）。
例外只有一类 —— **跨语言的元概念**，比如「语法糖」：它描述的是"写法"这件事本身，
不属于任何一门具体语言，因此**不存在任何一份语言规范会去定义它**。
这类词只能引权威第三方（如 Jargon File，"语法糖"这个术语的定名出处就在那一页），
出处一栏要写清它是什么性质的出处。

**② 引用编号可点**

正文里的 `[1]` 点一下，下面那张引用卡片会展开并滚进视野。

**③ 选中正文 → 左栏对应代码行高亮**

「逐词逐句」里写的 `第 7 行` 本来就是**原始代码的真实行号**，渲染时把它写进
DOM 的 `data-line-start`，选中那一段就能精确定位，不用去猜、也不用正则文本。
锚点找不到时（比如在技术溯源里选了一句），再拿选中的文字去原代码里逐行对；
两条路都落空就**不高亮、不报错**。

> 左栏是原生 `<textarea>`，**没法只给某几行加背景色**。所以底下垫了一层"镜像层"：
> 同字体、同字号、同行距、同内边距的 div，装着同一份文本（透明），只给命中的行上背景。
> 为什么不用 `(行号-1) × 行高` 硬算 —— 长行会折行，折行之后"逻辑第 N 行"在屏幕上
> 占几行就不确定了。镜像层的滚动条宽度是**实测**的（`offsetWidth - clientWidth`），
> 保证两边内容区严格相等、折行位置逐一相同。

**④ 就地追问，可多轮**

选中一段 → 浮出一个小「提问」按钮 → 展开问答面板，可以接着往下问。
对话历史由前端保存、随每次请求带上，`/api/ask` 保持**无状态**（不引存储、不管并发）。

带上去的历史有一个**长度预算**（不是按条数 —— 为什么、这个数怎么用实测定的，
见 [`docs/追问上下文预算说明.md`](docs/追问上下文预算说明.md)）。

## 知识库（M2）

这是项目"不只是调 API"的关键部分。

| | |
|---|---|
| **语料** | `server/rag/corpus.json` —— 人工整理的技术资料，每条带出处链接 |
| **向量** | `server/rag/corpus.embeddings.json` —— 离线预计算，**必须提交进 git** |
| **embedding 服务** | 智谱 `embedding-3`（1024 维），与生成回答的 DeepSeek **完全分开** |
| **检索** | 内存暴力算余弦，不装向量数据库（语料只有几十条） |
| **引用编号** | 服务端生成，通过响应头 `X-Rag-Sources` 传给前端，与正文 `[n]` 一一对应 |

**改了语料之后必须重跑：**

```bash
npm run rag:build      # 重新生成向量
```

否则新语料不会有向量（程序会检测到并跳过它们，不会给出错误答案）。

**语料变多后重新校准检索阈值：**

```bash
node --env-file=.env scripts/rag-probe.mjs
```

**想知道「检索到底带来了什么」，跑 A/B（需要本地 dev server 在跑）：**

```bash
npm run rag:ab
```

同一样本跑两遍 —— 一次带检索到的资料、一次不带，对比第四部分「技术溯源」。
两臂除「有没有资料」以外完全相同：A 臂打的就是本机的 `/api/analyze`（生产链路本身），
B 臂的提示词从 `server/utils/prompt.ts` 导入、模型参数照抄接口设置。
实测数据与结论见 [`docs/知识库设计说明.md`](docs/知识库设计说明.md) 的「那它到底有没有用」一节 ——
包括我们**说不出**「生成质量显著提升」这件事，以及为什么。

**优雅降级**：检索不到 / embedding 服务挂了 / 语料缺失 / 遇到未收录的语言（如 C++）
→ 自动退回纯模型回答，不报错、不白屏。

## 技术栈

| 层 | 选型 | 说明 |
|---|---|---|
| 框架 | **Nuxt 4**（Vue 3） | 前后端一体，服务端路由直接当后端用，不用单独买服务器 |
| 语言 | TypeScript | |
| 样式 | Tailwind CSS 4 | |
| 图渲染 | Vue Flow + dagre | 节点图渲染 + 自动排版 |
| 数据校验 | Zod | 校验接口入参 |
| 文本生成 | **DeepSeek**（`deepseek-chat`） | 生成四段解释文字 |
| 向量化 | **智谱 GLM**（`embedding-3`） | 把文字变成向量，供知识库检索 |
| 部署 | **阿里云 ECS（中国香港）+ Caddy** | 香港免备案；Caddy 自动申请并续期 HTTPS 证书、自动开 HTTP/2，反代本机 3000 —— **应用代码一行没改** |

> **为什么用两家不同的服务？**
> 生成文字和"把文字变成数字"是两种完全不同的模型，DeepSeek 不提供 embedding 接口。
> 国内通行做法就是**生成用一家、向量化用另一家**。两组配置在 `.env` 里完全分开，互不回退。

> **为什么不做单独的 Python 后端？**
> 大赛文档明确鼓励"充分利用现代前端框架的全栈能力（如 API Routes）简化后端逻辑"。
> Nuxt 的 `server/` 目录本身就是后端，少维护一套服务、少买一台服务器、少一次备案。

## 本地运行

**环境要求**：Node.js **^22.22.3 ‖ ^24.15.0 ‖ >=26**
（数字取自 nuxt 4.6.1 的 `engines`。本项目在 22.14 上实测过 —— 会触发 Nuxt 的"版本不受支持"警告，
虽然能跑但不建议；线上跑的是 22.23.3。）

```bash
# 1. 安装依赖
npm install

# 2. 配置密钥：复制模板
cp .env.example .env

# 3. 编辑 .env，至少填这两个（详见下一节）
#    NUXT_LLM_API_KEY=你的 DeepSeek key
#    NUXT_EMBEDDING_API_KEY=你的智谱 key

# 4. 启动开发服务器
npm run dev
#    打开 http://localhost:3000         首页（选入口）
#         http://localhost:3000/code    贴代码
#         http://localhost:3000/project 整个项目
```

> 只想看最基本的"贴代码 → 解释"效果：**只填 `NUXT_LLM_API_KEY` 就能跑**，
> 知识库检索会自动跳过（这是设计好的降级，不是报错）。

> **关于端口**：开发服务器默认用 **3000**。
> 如果这个端口被别的程序（比如另一个 Node 项目）占着，Vite 会自动换到 3001/3002 —— 留意终端里实际打印的地址。

| `NUXT_EMBEDDING_DIMENSIONS` | 可选 | `1024` | ⚠️ 改这个必须重跑 `npm run rag:build`，否则维度对不上 |

> ⚠️ **LLM 和 Embedding 是两家不同的服务，两组 key 不能互换。**
> 两家的向量空间不通用，拿错 key 只会得到 404 或维度错乱。

## 分层与依赖方向

依赖**单向**、不回头：`pages` → `components` / `composables` → `utils`。
（`types/` 与 `data/` 是被各层引用的数据与类型，不构成一层。）

| 层 | 管什么 | 不管什么 |
|---|---|---|
| `pages/` | 布局与编排：把面板拼起来、转接事件、持有原始代码 | 不实现面板内部的展示与交互 |
| `components/` | 展示与局部交互：props 进、事件出 | 同层的面板之间不互相引用 |
| `composables/` | 主链路的请求与状态 | 不碰 DOM、不碰滚动 |
| `utils/` | 纯函数：切分、定位、markdown 插件 | 不持有状态 |

三个面板（输入 / 解析结果 / 知识框架图）之间的协作一律由页面转接 ——
「查看 ↓」不直接调用图区，而是抛事件给页面。所以拿掉任意一个面板，
另外两个照样能跑；要改哪一块，也不用先去找它被谁引用。

## 我们怎么验证前端

改任何与渲染有关的东西之后，跑一次「红线校验」—— 它比"看截图"硬，而且不需要人看：

```bash
npm run dev          # 另开一个终端跑着
npm run cdp:verify   # 需要 headless Chrome 开着远程调试端口 9222
```

两条判据：

1. **红线：输出内容不许变** —— 把**浏览器渲染出的文字**与**接口返回的原文**（去掉 markdown 标记后）**逐字比对，必须相等**。抓的是"丢了半句话、术语被切碎、标签把文字吃掉"这类**眼睛看不出来**的问题。
2. **排版不许被挤动** —— 同一段落的高度必须相同，确认新加的标记没有把排版顶开。

**为什么是"同一次运行里比两端"，而不是"改前改后各跑一次再 diff"**：模型有 temperature，**每次输出长度都不同**，跨次 diff 没有意义。

`scripts/` 下还有两个同类探针：`npm run cdp:concurrency`（并发实测，量浏览器连接数上限）、`npm run cache:probe`（缓存命中，量公共前缀的顺序值多少钱）。三个脚本都从 `app/components/CodePane.vue` 读示例，保证"探针跑的样本"永远等于"演示用的样本"。
