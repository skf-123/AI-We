# 追问上下文预算说明

**追问带上去的对话历史，带多少才合适**

作者：石凯樊
2026-10-14

---

## 起因：一个「问到第 12 个问题就再也问不了」的现象

追问气泡上线后，我们顺着捋它的历史处理，问到一个问题：

> **历史对话会无限长吗？**

查下去发现：**不但会无限长，而且它根本撑不过第 12 个问题。**

`server/api/ask.post.ts` 里，请求体的历史被卡在 `max(20)` 条。而一轮问答是 **2 条**
（用户问一条、模型答一条），所以第 N 个问题带上的是 `2 × (N-1)` 条：

| 问第几个 | 带上几条 | 结果 |
|---|---|---|
| 第 11 个 | 20 条 | 刚好卡在上限 |
| **第 12 个** | **22 条** | **Zod 校验失败 → 400「请求参数有误」** |

**更糟的是它坏得很彻底**：报错之后历史只会继续涨，**后面每一次都超限**——
这个气泡从此再也问不出东西，只能关掉重开。

---

## 第一层判断：错的不在「20 太小」，在「用错了尺子」

第一反应是"把 20 调大"。但顺着想下去会发现，**条数这个度量本身就是错的**：

**它跟成本、延迟、上下文都没有对应关系。**

| | 条数限制的表现 |
|---|---|
| **短对话被误伤** | 问到第 12 个就封顶，哪怕每个问题都只有三个字、总共才几百字 |
| **长对话不被保护** | 三条各五千字的回答，条数没超，但请求早就又慢又贵了 |

真正让请求变大、变慢、逼近上下文上限的，是**字符数 / token 数**，不是有几条。

**该卡的是长度。**

---

## 第二层：那长度该给多少？——这件事不能猜

长度预算定多少，取决于一个我们**不知道**的事实：

> 输入变长，首字延迟会涨多少？

我先前是按"每秒处理两三千 token"估的，结论是"10 万 token 要等 40~60 秒"。
**但这是估的，不是测的。** 而项目里一直有条规矩：用事实代替猜测。

### 测量方法

直接打模型，量**首字延迟**（用户看到第一个字的时间），控制变量：

- 代码负载固定用最大的一份（19,574 字符，接近 2 万字符上限）= 最坏情况
- 系统提示词从 `server/api/ask.post.ts` 原样抽出来
- **只有历史的长度在变**

> 一个自指的细节：测量**必须绕开我们自己的接口**——因为那个接口正好被
> `max(20)` 挡着，根本发不出长历史。所以脚本直接打模型。

### 第一次测错了

第一版的结果是这样的（每档跑两次，取**较快**的一次）：

```
历史      0 字 → 340 ms
历史   5000 字 → 334 ms
历史  40000 字 → 937 ms
历史  80000 字 → 288 ms   ← 比 40000 字还快？
历史 150000 字 → 848 ms   ← 也比 40000 字快
```

**这些数字不单调。** 输入大了将近四倍，反而更快——这个反常说明**测法有问题**，不是"延迟和输入无关"。

检查下来是两个错叠在一起：

1. **每档跑两次、取较快的一次** —— 而第二次几乎必然命中**前缀缓存**。
   等于我系统性地在挑"缓存命中"的那次来报。
2. **历史是确定性生成的** —— 所以 15,000 字的历史，开头 5,000 字和"5,000 字档"
   **完全一样**。缓存按**前缀**命中，于是各档之间互相污染，差别被抹平了。

### 第二次：把缓存控制住

- 在系统提示词**最前面**插一段随机串 → 缓存必不命中（冷启动）
- 同一个规模先测冷、紧接着原样再发一次测热
- 把 `prompt_cache_hit_tokens` 一起取回来，**用它证明缓存到底命中没有**

结果（`npm run ask:probe` 的实际输出。括号里的"命中"数就是缓存控制有没有生效的证据：
冷启动全是 0，热的时候几乎全命中）：

| 历史 | prompt token | **冷启动首字** | **缓存命中首字** |
|---|---|---|---|
| 0 字 | 5,165 | 588 ms (命中 0) | 664 ms (命中 4,992) |
| 5,000 字 | 8,146 | 1,184 ms (命中 0) | 996 ms (命中 7,936) |
| 15,000 字 | 14,109 | 1,250 ms (命中 0) | 502 ms (命中 13,952) |
| 40,000 字 | 28,592 | 829 ms (命中 0) | 683 ms (命中 28,416) |
| 80,000 字 | 51,810 | 1,413 ms (命中 0) | 731 ms (命中 51,584) |
| 150,000 字 | **92,706** | **1,612 ms** (命中 0) | **731 ms** (命中 92,544) |

> **读数提醒**：单次测量的抖动有几百毫秒 —— 冷启动那列并不严格单调
> （比如 5,000 字那档 1,184 ms 反而比 40,000 字那档 829 ms 慢）。
> 所以看的是**趋势的量级**，不是单点数值。这也是为什么每一档都要把
> "缓存命中数"一起打出来：**先确认测法没坏，再看数字**。

**顺带标定了换算关系**（后面的参数就靠它）：

- **英文 / 代码 ≈ 0.3 token/字符**（19,372 字符的代码负载 → 5,165 token）
- **中文 ≈ 0.6 token/汉字**

---

## 第三层：结论与参数

### 结论一：延迟不是约束

从 5,165 token 涨到 **92,706 token**（**18 倍**），冷启动首字只从 0.6 秒涨到 **1.6 秒**。
**而且真实使用恰好是缓存命中的情形**——因为每一轮都在重发同一段前缀
（实测 92,706 个 prompt token 里命中 92,544，**99.8%**）。

> 这也顺带给"无状态 + 每轮重发历史"这个设计**正了名**：它不是在浪费，
> 它正好让前缀缓存吃得满满的。

**所以我先前那个"10 万 token 要等 40~60 秒"的估计，错了大约 30~100 倍。**
错在两点：按朴素吞吐估；**完全没算前缀缓存**。

### 结论二：预算按「最坏情况的账单」定，不按延迟定

既然延迟不是约束，那预算就不该拿"等不等得起"当尺子。改用另一个标准：

> **按最坏情况下的成本**，同时给上下文留足余量。

### 设计：一个可调变量 + 两条写死换算 + 一条护栏

| 层 | 内容 | 值 | 可调？ |
|---|---|---|---|
| **① 预算变量** | `askHistoryTokens` | 100000 | ✅ **唯一可调**（环境变量可覆盖） |
| **② 换算系数** | token ↔ 字符 | 0.6（取中文那档） | ❌ 写死 —— 物理关系 |
| **③ 条数护栏** | `HISTORY_ITEM_GUARD` | 5000 | ❌ 写死 —— 不参与决策 |

**② 为什么取 0.6 而不是 0.3**：取**较大的**那个是故意的 —— 这样算出来的字符预算，
无论历史里是中文还是代码，**实际 token 都不会超过预算**。代价是纯代码的历史
只用到一半额度：**保守，但不越界**。

**③ 为什么 5000 就够**：护栏的合格标准只有一条——**绝不先于长度预算触发**
（门闩要装得比门宽）。验算：护栏先触发需要"平均每条短于 166,666 ÷ 5000 = **33 字符**"，
而真实消息平均约 **175 字符**（问题约 20 + 回答约 330）——**差 5 倍多**。
它的职责只是挡畸形请求（比如塞进几万条空串让服务端白白解析）。

### 效果

| | |
|---|---|
| 字符预算 | 166,666（= 100000 ÷ 0.6） |
| 一轮典型问答 | 约 350 字符（问题约 20 + 回答约 330） |
| **能装** | **约 470 轮** |
| 打满时的首字延迟 | 冷启动约 1.7 秒、缓存命中约 0.5 秒 |
| 占 1M 上下文 | 约 10%，留 90% 余量 |

**从"10 轮就断"到"约 470 轮"**，而"要调"永远只有一个数可以动。

### 一处如实告知

裁掉更早的轮次时，**用户界面不会删掉它们**——用户往回翻仍然看得到，
只是模型不再"记得"。所以服务端在响应头 `X-Ask-History` 里把"实际带了几轮/共几轮"
告诉前端，气泡里显示一句：

> 更早的 N 轮已不再带给模型（仍显示在这里）

**走响应头而不是让前端自己算**，跟引用来源走 `X-Rag-Sources` 是同一个道理：
这是**服务端已经确定的事实**，两边各算一套迟早会漂移。

## 追问的其他输入上限（2026-10-20）

历史预算决定「带多少之前的问答」；下面几个上限决定「这一次请求本身能带多少」。
两件事分开：前者是给模型看多少，后者是接口接不接受。

| 字段 | 上限 | 为什么是这个数 |
|---|---|---|
| `code` | 50000 字符 | 项目模式带的是当前文件原文；项目解析时的单文件上限（代码里的 `FILE_MAX`）也是 50000。解析时看到多少，追问就带多少，否则两万到五万字符的文件会出现「能解析、不能问」。 |
| `selection` | 2000 字符 | 用户选中的那一小段；追问是局部解释，不需要整段正文。 |
| `question` | 500 字符 | 一个问题，不是一篇作文。 |
| `explanation` | 20000 字符 | 用户刚看过的那份四段解析。四段正文通常两三千字符，上限留出余量。 |
| `history` 条数护栏 | 5000 条 | 只负责「接不接受这个请求」；真正决定带多少的是上面的长度预算，两者顺序不能反。 |

`explanation` 是项目模式追问引入的可选字段，贴代码入口也会带。用户问「你上面说的第二点」时，不带这份解析，模型会另起一套说法；不传就是原来的行为。

---

## 明确不做的三件事

| | 为什么不做 |
|---|---|
| **把历史存到服务端** | 这段对话的生命周期**就等于气泡的生命周期**（关掉就该消失）。只为省"重发"的流量，换来一整套"谁创建、谁清理、什么时候过期"——不划算。而且用户会**贴自己的代码**，服务器上不留痕是个优点。（另外：**大模型没有"删除"能力**，"让模型自己决定删"这条路技术上不存在，删除责任永远在服务端代码上。） |
| **取消 `max_tokens`** | 它是**熔断**，不是限制。取消 = 把"最多花多少钱、最多等多久"交给模型和调用方——公网服务不能这么开。（主链路上限 2026-10-24 从 8,192 提高到 100,000 token，实际输出约 2,000~3,800 汉字，占比很小；上限留着是为了防最坏情况。） |
| **贴近 1M 上下文** | **装得下 ≠ 应该装。** 1M token 能装约 470 轮以上，但那是把"最坏情况的账单"放开了。 |

## 复现

```bash
# 1) 跑延迟实测 —— 直接打模型，绕开自家接口的上限（那正是要测的东西）
npm run ask:probe
#    脚本在 scripts/ask-latency-probe.mjs，会打印冷/热两条曲线，
#    并带上"缓存命中数"用来证明缓存确实被控制住了。

# 2) 验裁切逻辑（纯函数，不起服务）
#    server/utils/history.ts 的 trimHistory 可以直接断言：
#      · 累计字符不超预算
#      · 至少保留 1 条（哪怕单条就超预算）
#      · 保留的是最近的几条，且顺序不乱

# 3) 验接口层
#    构造 22 条 history 打 /api/ask → 应返回 200（而不是修复前的 400）；
#    历史总量超过字符预算时，响应头会带 X-Ask-History: {"usedRounds":…,"totalRounds":…}
```

**参数在哪**：

- `nuxt.config.ts` → `runtimeConfig.askHistoryTokens`（环境变量 `NUXT_ASK_HISTORY_TOKENS` 可覆盖）
- `server/utils/history.ts` → 换算系数（`TOKENS_PER_CHAR_WORST`）与条数护栏（`HISTORY_ITEM_GUARD`）
- `server/api/ask.post.ts` → 请求体各字段上限（`code` / `selection` / `question` / `explanation`）
