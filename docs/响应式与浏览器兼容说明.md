# 响应式与浏览器兼容说明

**支持的视口范围、一类容易踩的布局陷阱，以及浏览器版本要求**

麦穗团队 · 2026-10-12

---

## 一、支持的视口范围

页面的断点沿用 Tailwind CSS 的默认值，实际只用到两个：

| 断点 | 宽度 | 布局 |
|---|---|---|
| 默认（小屏） | < 640px | 单列，全部元素纵向堆叠，内距收窄 |
| `sm` | ≥ 640px | 内距恢复、正文恢复标准字号 |
| `lg` | ≥ 1024px | **切换为两栏**：左侧输入、右侧输出；两栏各自锁定一屏高度，内容在面板内部滚动 |

**实测范围**：320px ~ 1680px 逐档测量过（320 / 360 / 390 / 414 / 480 / 540 / 640 /
768 / 900 / 1000 / 1023 / 1024 / 1100 / 1280 / 1440 / 1680），Chrome 与 Edge 两个引擎各测一遍，
**均无横向溢出**。

**320px 是设计下限** —— 这是较老的小屏安卓与 iPhone SE 一类的宽度，能覆盖即基本通吃。

### 为什么按这些宽度取值

依据是公开的移动端视口统计（`StatCounter` 2026 年 9 月）与主流机型库（`yesviz` 等）。
关键结论只有一句：**移动端最主流的 CSS 视口集中在 360 ~ 430 之间**。

| 平台 | 最常见的 CSS 视口 |
|---|---|
| 安卓 | **360 × 800**（近邻还有 360×780、361×801，本质是同一批 360 宽机型） |
| 苹果（存量最大） | **414 × 896**（iPhone XR / 11 系列） |
| 苹果（在售主流） | **390 × 844**（13/14）、**393 × 852**（15/16） |

> ⚠️ **一个概念必须分清**：手机有「硬件像素」和「CSS 视口」两套尺寸，
> 媒体查询只认后者。例如 iPhone 16 的硬件分辨率是 1179 × 2556，
> 但 CSS 视口是 **393 × 852**（DPR = 3）。
>
> 安卓的 CSS 宽度**几乎永远挤在 360–412**，不会因为屏幕变大而线性变宽 ——
> 系统会自动调高 DPR。所以用「屏幕分辨率」推断前端布局是错的。

## 二、已经做的响应式处理

### 布局

- 两栏在 `lg` 以下自动堆叠为单列（`grid-cols-1` → `lg:grid-cols-2`），无需另写一套移动端结构
- 内容区 `max-w-[1400px] mx-auto`：宽屏居中，不无限铺开
- 长列表（示例按钮、图例、操作按钮行）一律 `flex-wrap`，放不下就换行而不是溢出

### 尺寸与触控

- 固定高度改为分档：图区小屏 300px / `sm` 以上 400px；输入框、输出区同理
- 主操作按钮在触屏上放大内距，接近移动端建议的触控尺寸
- 知识框架图的缩放/适配按钮，在触屏下面板放大到 32px（Vue Flow 默认仅 26px）

### 视口与手势

- **高度单位用 `dvh` 而不是 `vh`**。移动浏览器的地址栏会伸缩，`100vh` 会把页面撑破；
  `dvh` 会随可视区动态计算。根容器与错误页均已改用 `min-h-dvh`。
- **知识框架图在小屏下把纵向滑动手势交还页面**。
  Vue Flow 默认「单指拖动 = 平移画布」，并在触摸事件里阻止默认行为 ——
  结果是页面上想往下滑时，手指落在图上就变成拖图，页面纹丝不动。
  处理方式是在小屏给画布加 `touch-action: pan-y`：纵向滑动归浏览器（滚页），
  横向平移与双指缩放仍归 Vue Flow。**拖动节点不受影响**（节点保留原手势）。
- **解析结果区在小屏同样不许抢纵向滑动**（2026-10-17 修，见 commit `d93866b`）。
  输出容器带着 `overscroll-contain`（它本是为「`lg` 以上锁定一屏、面板内滚动」加的），
  但小屏上它没有固定高度、跟着内容长（实测 390 宽的手机上 **5728px 高、自身不可滚动**）
  —— 结果手势被它吃掉、又不许传给页面，**整页滑不动，只剩面板外侧约 30px 的窄边能滚**。
  **这个问题是在 Edge 上实际使用时暴露的**：改前那一版在 Chrome 上不复现。
  实测（仿真 390×844 + 合成触摸拖动）：正中 x=195 → **0px**，两侧 x=370 / x=20 → 345px；
  只把 `overscroll-behavior-y` 改回 `auto`（别的都不动），正中立刻恢复 345px。
  处理方式：给 `overscroll-contain` 加 `lg:` 前缀 —— **桌面行为不变**
  （computed 仍是 `contain`、面板仍可内部滚动）。

### 字号

输入框在窄屏使用 16px 字号。低于 16px 的可聚焦元素在 iOS 上会在聚焦时
自动放大整个页面，这是移动端最常见的一类「页面突然变大」现象。

## 三、一类容易踩的布局陷阱（项目约定）

**⚠️ grid / flex 的子项，必须显式声明 `min-w-0`，否则会被长内容撑宽整页。**

这是本项目约定，改动布局时请勿省略。

### 现象

输出内容里出现**长的、不含空格的字符串**时（长 URL、长标识符、长文件路径），
整页出现横向滚动条。实测一个 250 字符的无空格串会把页面撑宽 **1393px**。

### 原因

```
grid / flex 子项默认 min-width: auto
   → 最小宽度按「最长不可断词」计算
   → 长串把栅格轨道撑宽
   → 容器撑宽 → 面板撑宽 → 整页横向滚动
```

### 一个反直觉的点

**`break-words`（`overflow-wrap: break-word`）修不了这个问题。**
它只影响「行内如何折行」，**不影响元素的 `min-content` 宽度**，
所以栅格轨道照样被撑开。实测：加上 `break-words` 后溢出量仍是 1393px，一点没变。

要影响「最小宽度」，得用 `min-width: 0`（Tailwind 的 `min-w-0`），
或者 `overflow-wrap: anywhere`。**本项目采用前者**，写在两个栅格子项上：

```
app/pages/index.vue   →   两个 <section> 的 class 中都带 min-w-0
```

### 注意

这个陷阱**与屏幕宽度无关**，桌面端同样会触发。它不是「移动端问题」。

## 四、浏览器版本要求

**Tailwind CSS 4 要求较新的浏览器：Chrome / Edge 111+、Safari 16.4+、Firefox 128+。**

原因是 Tailwind 4 的输出用到了几项较新的 CSS 能力：`@property`、`color-mix()`、
层叠层（cascade layers）与原生 CSS 嵌套。

在版本过低的浏览器上，**样式表会整体失效**，页面退化成无样式的裸 HTML ——
表现出来就是「排版全乱、出现横向滚动条」。遇到这种现象时，第一件事是确认浏览器版本，
而不是排查布局代码。

> 本项目的开发环境为 Windows + Edge / Chrome 最新版。

## 五、已知限制

| 限制 | 说明 | 状态 |
|---|---|---|
| **面板高度锁定 `100vh`** | 两栏在 `lg` 以上锁定「一屏高度」。在**超高屏**（如 1440p 桌面显示器）上，卡片被拉成 1200px 以上，内容集中在顶部、中间大片空白 | 待改（方向：给面板高度设上限，而非继续加断点） |
| **手机端信息架构** | 窄屏只是把桌面的「两栏 + 下方图」纵向堆叠，初始状态会出现三段较大的空白区域。功能齐全，但不算为手机重新设计过 | 待重做 |
| **长文档的可读性** | 四段解释在手机上是很长的竖向滚动 | 已知，未处理 |
| **横屏手机 / 平板** | ≥1024px 的**触屏**设备会套用桌面那套「锁定一屏 + 面板内滚动」，在触屏上滚动体验欠佳。彻底修需按 `@media (pointer: fine)` 分派，而不是按宽度 | 待改 |

## 六、调试移动端时的注意

1. **不要用物理分辨率当 CSS 视口。** 设备工具栏里选预设时，确认其中给出的是
   **CSS 尺寸**（如 iPhone XR 是 414 × 896），而不是厂商宣传的硬件分辨率
   （如 3200 × 1440）。若数字大得离谱，先怀疑它给的是物理像素。
2. **安卓 360 宽是硬门槛。** 布局若在 360px 下不溢出，基本通吃全部安卓机型。
3. **必测的最小机型集合**：`iPhone SE3`(375) / `iPhone 14`(390) / `Redmi`(360) /
   `Galaxy S24`(360×780) / `Pixel`(412)。
4. 高度相关的问题优先怀疑 `vh`，宽度相关的问题优先怀疑 `min-width: auto`。
