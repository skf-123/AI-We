# 知识库设计说明

**为什么我们的语料是一张张「卡片」，而不是下载来的文档**

作者：石凯樊
2026-10-11（2026-10-15 补：检索的实现，以及实测出来的效果边界）

---

## 起因：陈裔华提的一个疑问

整理语料的时候，陈裔华翻到 `server/rag/corpus.json`，看了一会儿问：

```json
{
  "id": "py-class-init-self",
  "lang": "python",
  "tags": ["class", "self", "oop", "init"],
  "title": "类、__init__ 与 self",
  "content": "Python 的类用 class 定义，__init__ 是「对象造好之后自动调用」的初始化方法，作用是给对象挂上初始属性。self 代表「当前这个对象本身」，必须写成方法的第一个参数 —— 这一点和其他语言不同：Java、C++ 里 this 是隐式存在的关键字，Python 则把它显式写出来。显式的好处是「obj.method() 其实是 Class.method(obj)」这件事一眼可见，不会让人误以为方法和对象是绑死的。代价是每个方法都要多写一个 self。注意 __init__ 只负责初始化，真正「创建对象」的是 __new__，只是绝大多数情况下不需要自己写它。",
  "source": {
    "label": "Python 文档 · 类",
    "url": "https://docs.python.org/zh-cn/3/tutorial/classes.html"
  }
}
```

> 这不太对吧？知识库不应该是一堆**文档文件**堆在本地吗？
> 现在这样，正文只有两百多字，后面挂个链接 —— **是不是太薄了？这是不是偷懒？**
>
> 而且我本来以为，做一个知识库应该是**很大的工作量**啊。

下面是我们讨论之后理出来的结论。

---

## 核心判断：我们要的答案，根本不在那些文档里

拿上面那条 `__init__` 与 `self` 举例。我们写的内容里，最有价值的是这一句：

> 显式的好处是「`obj.method()` 其实是 `Class.method(obj)`」这件事一眼可见，不会让人误以为方法和对象是绑死的。
> 注意 `__init__` 只负责初始化，真正「创建对象」的是 `__new__`。

**这句话在 Python 官方文档里吗？不在。**

如果你打开 `docs.python.org/3/tutorial/classes.html`，你会看到：类的语法、方法怎么定义、继承规则、成段的示例代码……

但**不会有人用一句话告诉你：为什么 Python 要把 `self` 显式写出来，而 Java 不用。**

那是老师在课堂上才会讲的话。

而我们的功能叫**「技术溯源」**，它问的恰恰是这三个问题：

1. 这项技术**为什么**被发明出来？
2. 它当初**解决**了什么痛点？
3. 它大致**怎么演化**到今天的？

**这三个问题，官方文档基本都不直接回答。**

文档回答的是「怎么用」，不是「为什么会有它」。

---

## 所以「下载整篇文档」这条路的真实代价

他原来的想法是：把 MDN、Python 官方文档这些整站抓下来，放进本地，检索的时候去里面找。

把数字摆出来之后，想法就变了：

| | 我们现在的做法 | 走「下载整篇文档」 |
|---|---|---|
| 体量 | **58 条，约 2 万字，55 KB** | MDN 整站**数百 MB** |
| 单条粒度 | 约 350 字，讲清一个概念 | 单篇 MDN 页面约 200 KB，**其中九成是 API 参数表** |
| 能不能进 git | ✅ 55 KB，随代码一起提交 | ❌ 几百 MB，评委 clone 不下来，只能部署时下载 |
| 还需要什么 | 无 | 还得清洗 HTML、切分成块、装向量数据库 |

关键不在于大小，在于**这些文档的形状不对**：

一篇 MDN 的 `Array.prototype.reduce` 页面里，有语法、参数表、返回值、示例、浏览器兼容性表格。
**唯独没有**「它 2009 年随 ES5 进入标准，目的是让求和这类操作不必手写 for 循环，把『怎么累积』从『怎么遍历』里解耦出来」——而这句才是我们要的。

---

## 工作量其实是**倒挂**的

原本以为「抓文档」能省事，实际上正好相反：

```
抓整篇文档这条路的实际流程：

  下载整站 → 清洗 HTML → 切成小块 → 建索引 → 装向量数据库 → 部署
                                                              │
                                              ……做到这里，发现要的答案还是没有
                                                              │
                                                还是得自己动笔写「为什么会有它」
```

```
我们这条路的流程：

  直接写那句「为什么会有它」   ← 工作量主要在这里，也是唯一真正有价值的部分
```

也就是说：**抓文档 = 多做一堆脏活，核心的那句话仍然要自己写。**

更麻烦的是工程上的现实问题：几百 MB 的语料进不了代码仓库。评委 clone 下来是没有文档的，只能靠部署时联网下载 —— 网络一抖动，演示当场翻车。而我们这种「构建期就把向量算好、随代码提交」的做法，没有任何运行时依赖。

## 打个比方

| 做法 | 像什么 |
|---|---|
| 下载整篇文档 | 把**整个图书馆搬回家**。找东西要翻很久，而且你想问的那句「这本书当初为什么被写出来」，书里没写 |
| 我们的做法 | **自己整理一张张卡片**。正面讲清一个概念，背面写着「想深究去看哪本书第几页」 |

**我们做的不是「文档的搬运」，是「知识的提炼」。**
这两件事的工作量不在一个方向上。

---

## 但这个方法也有代价，我不回避

**覆盖窄。**

编程世界的概念成千上万，我们目前只整理了 58 条。所以会出现两种情况：

- 用户贴的代码用到**已收录**的概念 → 正文里会标注 `[1][2]`，下方出现引用卡片，点开能看到我们写的内容
- 用到**没收录**的 → 检索不到，就不会有引用卡片（这是设计好的降级，不是报错，主流程完全不受影响）

也就是说，**覆盖范围是完全由我们的语料规模决定的**。

这也是为什么这个项目后面还要继续补语料 —— 不是「再去下载更多文档」，而是**继续写卡片**。每一条都是一次提炼，没有捷径。

---

## 为什么不干脆接一个联网搜索

我们也考虑过另一条路：接一个搜索 API（比如博查），检索时直接联网搜。

它能解决覆盖问题 —— 什么概念都能搜到。但我们最后没有采用，原因有两个：

**第一，它会改变这个项目的定位。**

如果引用来源变成「搜出来的网页」，那这个项目就从「**我们有一份自己整理的知识库**」变成了「**我们会调用搜索**」。前者是作品，后者只是一个功能。评委会看的就是这个区别。

**第二，它会引入不受控的不确定性。**

- 每次回答都依赖一次外部网络请求，慢，而且会失败
- 搜出来的内容质量参差不齐，官方文档和营销博客混在一起
- 演示的时候多一个可能翻车的环节

所以我们的选择是：**守住自己的语料库**。

如果以后确实需要扩大覆盖，正确的做法也是**继续把卡片一张张写进去**，而不是把判断权交出去。

## 我们的检索是怎么实现的（以及为什么没有索引）

先把代码在哪说清，免得找：

| 层 | 位置 | 干什么 |
|---|---|---|
| **本体** | `server/rag/` | `corpus.json` 语料、`corpus.embeddings.json` 向量、`corpus.ts` 加载与校验、`embed.ts` 调智谱向量化、`retrieve.ts` 检索 |
| **唯一的检索入口** | `server/api/analyze.post.ts` | 主链路只在这一处调检索 |
| **引用卡片** | `server/api/source/[id].get.ts` + `app/components/SourceList.vue` | 点开一条引用，按 id 取语料正文 |
| **离线工具** | `scripts/build-embeddings.mjs`、`scripts/rag-probe.mjs` | 改了语料重算向量；校准检索阈值 |

检索本身只有三步：**判断语言 → 逐条算余弦 → 按阈值取前 4 条**。

**这里要说清一件事：我们没有索引。**

没有向量数据库，没有 ANN（近似最近邻）索引，没有倒排表。就是拿查询向量跟候选里的每一条**逐一算余弦**，然后排序取前几名。

理由只有一条：**58 条 × 1024 维，全算一遍用不了 1 毫秒。** 为了这点时间装一套向量数据库进来，要多维护一个组件、多一个可能挂掉的环节 —— 不划算。

所以**别说"我们实现了向量索引"**，准确的说法是「**规模小到不需要索引**」。什么时候需要？语料涨到几万条以上；那时换 ANN 是 `retrieve.ts` 里一个函数的局部改动，不影响其他地方。

> 顺带记一条实测出来的结论：**语言过滤这一层是逼出来的，不是想出来的。**
> 一开始只靠相似度阈值，实测发现 embedding 模型**分不开「相关」和「不相关」**——
> C++ 代码对 JS 语料也能拿到 0.57 的相似度，因为向量空间里「这是代码」的权重远大于「这是关于什么的」。
> 所以检索前先判断代码是什么语言，只在该语言的资料里找；遇到没收录的语言（C++、Go、Rust）直接跳过检索。
> 详见 `server/rag/retrieve.ts` 顶部的注释。

## 那它到底有没有用 —— 我们量了一遍

评分表里对着 RAG 那一项，写的是一句很硬的话：

> **生成质量是否因检索增强而显著提升**

这句要的是**证据**，不是「我们实现了 RAG」。而我们在很长一段时间里答不出来 —— 因为这个知识库从做出来的第一天就在，**没留过「没有它」的样子**。

后来发现其实能测：**把开关关掉就是那个样子**。当初定降级路径时有一条规矩 —— 没检索到资料时系统提示词**一个字都不变**，所以「关掉检索」和「改造前」是等价的。

于是写了一个 A/B 探针（`npm run rag:ab`，需要本地开发服务器在跑）：

- **A 臂（开）**：直接打本机的 `/api/analyze` —— 那就是生产链路本身，检索、组提示词、调模型全走真的
- **B 臂（关）**：脚本自己组一份「没有资料」的提示词；系统提示词从 `server/utils/prompt.ts` 导入（不复制一份），模型参数照抄接口里的设置
- 两臂的差异**只有**：一段参考资料使用规则 + 一个「参考资料」块

**三个内置示例，各跑一次：**

| 样本 | 开 RAG 第四部分 | 引用 | 关 RAG 第四部分 | 引用 |
|---|---|---|---|---|
| JS · 数组处理 | 727 字 | 11 处 | 798 字 | 0 |
| Python · 装饰器 | 1180 字 | 3 处 | 979 字 | 0 |
| Python · 有安全隐患 | 673 字 | 5 处 | 865 字 | 0 |
| **平均** | **860 字** | **19 处** | **881 字（−2%）** | **0** |

**一条稳、一条不稳，必须分开说。**

**稳的是引用。** 开 RAG 时有引用编号（这一轮 19 处），关 RAG 时**一处都没有** —— 跨两次实测、8 个样本，**没有例外**。这不是「多一点少一点」，是**有和没有**。

**不稳的是长度。** 这一轮平均 **−2%**（三个样本里两个是关 RAG 反而更长）；而前一晚另一次实测，同一族样本平均**长 38%**。**同一段代码两次跑，一个正一个负** —— 长度这个指标的方差盖过了效应，**不能拿它当结论**。

**所以真正说得住的，是机制上的差异 —— 而那个要看内容才看得出来。**

拿「Python · 有安全隐患」举例。关 RAG 的版本讲了 2 个点（函数定义、字符串拼接）；开 RAG 的讲了 5 个点，多出来的三个是：

> **4. 参数化查询（这段代码没有用，但必须知道）**
> **5. 关于异常处理（这段代码也没用，但相关）**
> 以及 DB-API 与游标：为什么换数据库时业务代码几乎不用改

**关键在「这段代码没有用，但必须知道」这句。** 检索是按语义相似度找的，找到的资料是「SQL 注入」和「异常处理」，于是模型**把这段代码里缺的、该知道的解药一并讲了出来**。关 RAG 的版本只讲「代码里有什么」，**不会主动补这一块** —— 而对一个贴了有漏洞代码的人来说，「这里还应该有什么」恰恰是他最需要的。

### 所以：能说什么，不能说什么

**能说**
- **可追溯**：引用编号从 0 到有，每句都能点开看原文 —— 稳定
- **会补邻近知识**：把「代码里没有、但和它强相关」的东西带进来 —— 在语料覆盖到的点上很明显

**不能说**
- ❌ **「生成质量显著提升」**。关键事实两边都对（ES5 是 2009、PEP 318、Python 2.4 —— 关 RAG 也全对），长度上又说不出稳定的幅度

**为什么说不出？因为语料的选材决定了增益的上限。** 我们收的全是**模型本来就知道**的经典知识（ES6、装饰器、GIL）—— 这类知识，RAG 换不来「它知道」，只换得来「它有出处」。真要换来知识增量，语料里就得放**模型记不准或不知道**的东西（新规范、冷门方言差异、容易记错的年份归属）。

**最后一句限定**：上表是**三个样本各跑一次**。样本量小、模型有温度 —— 所以我们主张的是**机制**，不是**幅度**。谁去复现，看到的数字都会和上表不一样，但「引用从无到有」这一条应该是一致的。

## 结论

知识库这件事，一开始我们都以为难在「怎么把海量文档搞进来」。

讨论之后才发现：**难点从来不在采集，在提炼。**

- 官方文档告诉我们「怎么用」——这不难获取，但对我们的功能没用
- 我们要回答的是「为什么会有它、它解决了什么、怎么走到今天」——**这些只能自己写下来**

所以我们的知识库不是一份文档的副本，而是一份**我们自己对技术来龙去脉的理解**，每一条都挂着官方出处供人查证。

它现在只有 58 条，之后会继续长。但每一条都是手写的，这是这个项目里我最不想走捷径的地方。
