# 知识库设计说明

**为什么我们的语料是一张张「卡片」，而不是下载来的文档**

作者：石凯樊
2026-10-11

## 核心判断：我们要的答案，根本不在那些文档里

拿上面那条 `__init__` 与 `self` 举例。我们写的内容里，最有价值的是这一句：

> 显式的好处是「`obj.method()` 其实是 `Class.method(obj)`」这件事一眼可见，不会让人误以为方法和对象是绑死的。
> 注意 `__init__` 只负责初始化，真正「创建对象」的是 `__new__`。

**这句话在 Python 官方文档里吗？不在。**

如果你打开 `docs.python.org/3/tutorial/classes.html`，你会看到：类的语法、方法怎么定义、继承规则、成段的示例代码……

但**不会有人用一句话告诉你：为什么 Python 要把 `self` 显式写出来，而 Java 不用。**

那是老师在课堂上才会讲的话。

而我们的功能叫**「技术溯源」**，它问的恰恰是这三个问题：

1. 这项技术**为什么**被发明出来？
2. 它当初**解决**了什么痛点？
3. 它大致**怎么演化**到今天的？

**这三个问题，官方文档基本都不直接回答。**

文档回答的是「怎么用」，不是「为什么会有它」。

---

## 所以「下载整篇文档」这条路的真实代价

他原来的想法是：把 MDN、Python 官方文档这些整站抓下来，放进本地，检索的时候去里面找。

把数字摆出来之后，想法就变了：

| | 我们现在的做法 | 走「下载整篇文档」 |
|---|---|---|
| 体量 | **31 条，8495 字，29 KB** | MDN 整站**数百 MB** |
| 单条粒度 | 274 字，讲清一个概念 | 单篇 MDN 页面约 200 KB，**其中九成是 API 参数表** |
| 能不能进 git | ✅ 29 KB，随代码一起提交 | ❌ 几百 MB，评委 clone 不下来，只能部署时下载 |
| 还需要什么 | 无 | 还得清洗 HTML、切分成块、装向量数据库 |

关键不在于大小，在于**这些文档的形状不对**：

一篇 MDN 的 `Array.prototype.reduce` 页面里，有语法、参数表、返回值、示例、浏览器兼容性表格。
**唯独没有**「它 2009 年随 ES5 进入标准，目的是让求和这类操作不必手写 for 循环，把『怎么累积』从『怎么遍历』里解耦出来」——而这句才是我们要的。

---

## 工作量其实是**倒挂**的

原本以为「抓文档」能省事，实际上正好相反：

```
抓整篇文档这条路的实际流程：

  下载整站 → 清洗 HTML → 切成小块 → 建索引 → 装向量数据库 → 部署
                                                              │
                                              ……做到这里，发现要的答案还是没有
                                                              │
                                                还是得自己动笔写「为什么会有它」
```

```
我们这条路的流程：

  直接写那句「为什么会有它」   ← 工作量主要在这里，也是唯一真正有价值的部分
```

也就是说：**抓文档 = 多做一堆脏活，核心的那句话仍然要自己写。**

更麻烦的是工程上的现实问题：几百 MB 的语料进不了代码仓库。评委 clone 下来是没有文档的，只能靠部署时联网下载 —— 网络一抖动，演示当场翻车。而我们这种「构建期就把向量算好、随代码提交」的做法，没有任何运行时依赖。

## 打个比方

| 做法 | 像什么 |
|---|---|
| 下载整篇文档 | 把**整个图书馆搬回家**。找东西要翻很久，而且你想问的那句「这本书当初为什么被写出来」，书里没写 |
| 我们的做法 | **自己整理一张张卡片**。正面讲清一个概念，背面写着「想深究去看哪本书第几页」 |

**我们做的不是「文档的搬运」，是「知识的提炼」。**
这两件事的工作量不在一个方向上。

---

## 但这个方法也有代价，我不回避

**覆盖窄。**

编程世界的概念成千上万，我们目前只整理了 31 条。所以会出现两种情况：

- 用户贴的代码用到**已收录**的概念 → 正文里会标注 `[1][2]`，下方出现引用卡片，点开能看到我们写的内容
- 用到**没收录**的 → 检索不到，就不会有引用卡片（这是设计好的降级，不是报错，主流程完全不受影响）

也就是说，**覆盖范围是完全由我们的语料规模决定的**。

这也是为什么这个项目后面还要继续补语料 —— 不是「再去下载更多文档」，而是**继续写卡片**。每一条都是一次提炼，没有捷径。

---

## 为什么不干脆接一个联网搜索

我们也考虑过另一条路：接一个搜索 API（比如博查），检索时直接联网搜。

它能解决覆盖问题 —— 什么概念都能搜到。但我们最后没有采用，原因有两个：

**第一，它会改变这个项目的定位。**

如果引用来源变成「搜出来的网页」，那这个项目就从「**我们有一份自己整理的知识库**」变成了「**我们会调用搜索**」。前者是作品，后者只是一个功能。评委会看的就是这个区别。

**第二，它会引入不受控的不确定性。**

- 每次回答都依赖一次外部网络请求，慢，而且会失败
- 搜出来的内容质量参差不齐，官方文档和营销博客混在一起
- 演示的时候多一个可能翻车的环节

所以我们的选择是：**守住自己的语料库**。

如果以后确实需要扩大覆盖，正确的做法也是**继续把卡片一张张写进去**，而不是把判断权交出去。

---

## 结论

知识库这件事，一开始我们都以为难在「怎么把海量文档搞进来」。

讨论之后才发现：**难点从来不在采集，在提炼。**

- 官方文档告诉我们「怎么用」——这不难获取，但对我们的功能没用
- 我们要回答的是「为什么会有它、它解决了什么、怎么走到今天」——**这些只能自己写下来**

所以我们的知识库不是一份文档的副本，而是一份**我们自己对技术来龙去脉的理解**，每一条都挂着官方出处供人查证。

它现在只有 31 条，之后会继续长。但每一条都是手写的，这是这个项目里我最不想走捷径的地方。
